** Reading the flowchart

- A rounded box is something the game *prints*.
- A diamond is a question the game *asks with input()*, with one arrow
  out per possible answer.
- Notice that two of the three diamonds only have *one* good answer
  ("Left", "Wait") — every other answer, including the other labeled
  option ("Right", "Swim"), leads to the same "Game Over." Only the
  *last* diamond ("Which door?") has four genuinely different
  outcomes, one per color plus a catch-all.

That difference matters for how you write the conditions: the first
two diamonds are really just "right answer vs. everything else" (an
~if~ / ~else~ is enough), while the last one needs ~if~ / ~elif~ /
~elif~ / ~else~ to tell all four branches apart.

** Reminder: how ~input()~ works

#+begin_example python

  print("You typed:", answer)
#+end_example

~input()~ always returns a *string* — compare it to another string
with ~==~, exactly like ~"left"~.

* Solution (with functions)

The three questions all follow the same shape — ask, normalize, look
up what happens next — so that shape is what gets pulled into
functions, not each branch individually. The data (which answers lead
where, and what each wrong answer says) moves into module-level
dictionaries, separate from the logic that walks through them.

#+begin_src python
  LOCATIONS = {
      "crossroads": {
          "moves": {"left": "river"},
          "wrong": "Fall into a hole. Game Over.",
      },
      "river": {
          "moves": {"wait": "doors"},
          "wrong": "Attacked by trout. Game Over.",
      },
      "doors": {
          "moves": {"red": "fire", "blue": "beasts", "yellow": "win"},
          "wrong": "Game Over.",
      },
  }

  PROMPTS = {
      "crossroads": "You're at a crossroad. Left or right? ",
      "river": "You've come to a lake. Swim or wait for a boat? ",
      "doors": "Which door — red, blue, or yellow? ",
  }

  ENDINGS = {
      "fire": "Burned by fire. Game Over.",
      "beasts": "Eaten by beasts. Game Over.",
      "win": "You Win!",
  }

  def welcome_screen():
      print("Welcome to Treasure Island.")
      print("Your mission is to find the treasure.")

  def get_choice(prompt):
      """Ask a question, return the answer normalized to lower case."""
      return input(prompt).lower()

  def try_move(location, choice):
      """Return the next location/ending for choice, or None if choice is invalid here."""
      return LOCATIONS[location]["moves"].get(choice)

  def play():
      location = "crossroads"

      while location in LOCATIONS:
          choice = get_choice(PROMPTS[location])
          destination = try_move(location, choice)

          if destination is None:
              print(LOCATIONS[location]["wrong"])
              return

          location = destination

      print(ENDINGS[location])

  def main():
      welcome_screen()
      play()

  if __name__ == "__main__":
      main()
#+end_src

*Why this generalizes:* adding a fourth location — say a cave past
the doors — means adding one entry to =LOCATIONS=, one to =PROMPTS=,
and (if it's an ending) one to =ENDINGS=. Nothing about =try_move= or
=play= has to change: neither one knows how many locations there
are or what they're called, they just follow whatever =LOCATIONS=
currently says. That's the payoff of separating data from logic —
the *shape* of the game (ask, normalize, look up, move or end) stays
fixed in code, while the *content* (how many locations, what they
say, where they lead) lives entirely in data you can edit without
touching a function.
